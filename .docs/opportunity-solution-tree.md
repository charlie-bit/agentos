# 机会解决方案树

> 基于 Teresa Torres《持续发现习惯》框架。2026-09-07 按"插件化 Agent 执行框架"重写。

## 期望结果（第 0 层）

**让一个 Agent 开发者用 preset.yml 在三分钟内切换整个技术栈（模型供应商、工具集、知识库后端），不改动一行业务代码。**

衡量指标：**preset 切换成功率** — 同一 preset 在不同运行时中，从 manifest 加载到所有 Provider 挂载成功的比例。

平台的生死指标是**契约采纳率**：6 个月内 ≥ 3 个第三方 Provider 实现通过 conformance test suite。

## 机会点（第 1 层）— 三类用户视角

### 用户画像 A：Agent 开发者（在 LangGraph / CrewAI / DSH / SDK 上构建）

| # | 机会点 | 重要性 | 满意度 | 机会得分 |
|---|--------|--------|--------|---------|
| O1 | 我的 agent 绑死了一个模型供应商，换供应商要改路由表+降级链+token 管理 | 5 | 1 | **2.00** |
| O2 | 每加一个新工具就要写适配器，不同运行时对 MCP 的支持不一致 | 4 | 2 | **1.50** |
| O3 | 知识库知识注入散落在 system prompt / skill / MCP 工具里，没有统一的管理方式 | 4 | 1 | **1.50** |

### 用户画像 B：框架作者（自建或维护 Agent 运行时）

| # | 机会点 | 重要性 | 满意度 | 机会得分 |
|---|--------|--------|--------|---------|
| O4 | 每次新加一个 Provider 类型都要重新设计接口和挂载逻辑 | 4 | 2 | **1.50** |
| O5 | 想让使用者配置模型/工具/知识库但不想暴露凭证管理 | 3 | 2 | **1.25** |

### 用户画像 C：技术负责人（管理多团队的多套 Agent）

| # | 机会点 | 重要性 | 满意度 | 机会得分 |
|---|--------|--------|--------|---------|
| O6 | 不同团队的 agent 各用不同的知识库后端，迁移成本极高 | 4 | 2 | **1.50** |
| O7 | 无法批量更新底层 provider（如升级向量检索引擎）而不改业务代码 | 3 | 2 | **1.25** |

### 优先级最高的机会点

1. **O1** — 模型绑定是最普遍的痛点，所有 agent 项目都面临
2. **O3 + O4** — 知识注入和 Provider 抽象是框架作者的共同挑战
3. **O2** — MCP 生态成熟后是天然切入点

## 方案（第 2 层）

### 针对 O1/O2/O3（模型绑定、工具适配、知识碎片）

| # | 方案 | 来源 | 描述 |
|---|------|------|------|
| S1 | **三契约定义** | 架构 | KnowledgeProvider（五动词）+ ToolProvider（manifest 格式）+ ModelProvider（路由+降级）。runtime-free 资产。 |
| S2 | **preset 引用模型** | 产品 | 一文件引用所有 provider；凭证只留 tokenEnv，不进 manifest。换业务 = 换文件。 |
| S3 | **四层四元组（Manifest→Contract→Loader→Registry）** | 架构 | 知识库/模型/MCP/入口四层共享同一模式，不各做一套。 |

### 针对 O4/O5（框架作者的 Provider 抽象）

| # | 方案 | 来源 | 描述 |
|---|------|------|------|
| S4 | **Conformance Test Suite** | 质量 | 每个契约配黑盒测试，CI 运行。第三方接入者的唯一准入标准。 |
| S5 | **provider-sdk** | 工程 | 最小骨架生成器：`agentos init-provider <type> <name>` → 脚手架 + conformance stub |

### 针对 O6/O7（团队级知识迁移）

| # | 方案 | 来源 | 描述 |
|---|------|------|------|
| S6 | **provider-markdown** | 工程 | git+markdown 源真相层 + index 生成器 + CI lint。零依赖兜底，任何人能立刻开始。 |
| S7 | **跨运行时示例 preset** | 文档 | 同一 preset 在 Claude Agent SDK 和另一运行时中的落地对比，证明可移植性。 |

## 实验（第 3 层）

### 实验 E1 — 契约可用性验证（验证 S1/S2/S3）

- **假设：** 外部开发者看完三契约文档后，能用 preset.yml 挂上一个真实工具和知识库。
- **方法：** 发布三契约草案 + preset example + provider-markdown，邀请 5 位有 agent 项目经验的开发者试用。
- **指标：** 30 分钟内独立完成一次 preset 声明 + provider 实例化 + 查询。
- **成功阈值：** ≥ 3/5 在规定时间内完成，无重大理解障碍。

### 实验 E2 — Conformance Test Suite 有效性（验证 S4）

- **假设：** 黑盒测试能检测出 provider 实现的关键缺陷（而非只捕获边缘 case）。
- **方法：** 故意破坏 provider-markdown 的 3 个核心行为，验证 conformance suite 能否全部捕获。
- **指标：** 捕获率 100%；误报率 < 10%。
- **成功阈值：** 所有故意破坏都被检测到，且不阻断正常行为。

### 实验 E3 — 跨运行时可移植性（验证 S7）

- **假设：** 同一 preset.yml 能在两个不同运行时中驱动相同的 provider 组合。
- **方法：** 编写一份包含 markdown KB + OpenAI model + 一条 MCP tool 的 preset，分别在两个运行时中加载并跑通。
- **指标：** 两个运行时都通过 conformance 全绿。
- **成功阈值：** 一次通过或 ≤ 2 次修正后通过。
