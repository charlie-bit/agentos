0.2 逐个比较（主参考 5 个）

0.2.1 DeepSeek Harness（266k）—— 重合度最高，哲学相反

项内容
它是什么MIT、TypeScript，"Everything is a Plugin"，底层是 vendor 的 Cordis 元框架。没有特权内核：agent loop、模型适配、工具注册、会话日志、system prompt 全是可替换插件。profile / bundle / patch 三层 YAML 层叠，255 个包。
我们取什么插件边界、profile/bundle/patch、append-only 会话日志、subagent/teams、沙箱后端（bwrap/Landlock/Seatbelt）、能力接缝的三角色划分。
我们不取什么Cordis 绑定（契约只在 DSH 内有效）、无特权内核的工程预算（我们没有 255 包的人力）、"把竞品装进来"的单体运行时哲学。
我们要补什么事件日志版本迁移、bundle/patch 的分层语义、team roster / task board / mailbox。
判定架构参照第一名。v1 曾想把它做成第一个 conforming runtime；v2 明确不做跨运行时，所以只做设计参照，不做兼容层。

0.2.2 OpenHands / Agent Canvas（92k）—— 定位是平台，不是内核

项内容
它是什么自托管的 coding agent 控制中心。核心卖点是 ACP（Agent-Client Protocol）：可以跑 OpenHands、Claude Code、Codex、Gemini、Pi、OpenCode，后端可在本地 / Docker / VM / 云之间切换；带 Slack/GitHub/Linear 自动化和自托管 UI。
我们取什么沙箱后端分层（T0–T3）、平台形态、Web UX、对外暴露 MCP、自动化的触发方式。
我们不取什么ACP 聚合第三方 agent——我们跑 model，不跑 Claude Code / Codex 这类 agent；也不做多后端切换的运营面。
我们要补什么容器/远程沙箱、常驻自动化（schedule/webhook）、平台级 UI。
判定平台参照第一名。ACP 只作为未来可选入口，不作为核心；核心仍是 model-agnostic 的 harness。

0.2.3 OpenAI Agents SDK（30k）—— agent-as-tool 的最佳参照

项内容
它是什么轻量 agent 框架：agent loop、handoff、guardrails、tracing、sessions（SQLite）、MCP。Python 优先，模型以 OpenAI 为主。
我们取什么agent-as-tool、handoff、guardrails（映射到 policy engine）、tracing 的 span 语义、session 持久化。
我们不取什么OpenAI-only、Python-only、把编排留在代码里（我们要 profile 化）。
我们要补什么guardrails 作为 ControlPlane 的 policy、handoff 作为 group chat 的一种、trace 的父子 span。
判定组件级参照。它证明 8 个窄 API 里的 stream / invoke / record 足够表达 agent 循环。

0.2.4 SWE-agent（20k）—— coding loop 的最佳参照

项内容
它是什么单任务 coding agent：agent-computer interface（ACI）、Docker 环境、trajectory 日志、评测。
我们取什么代码任务循环、环境交互、eval / golden set、trajectory 回放、sandbox 的 exec 语义。
我们不取什么单一 coding 场景、单任务模型。
我们要补什么eval 作为 ControlPlane 的一部分；sandbox T1/T2 的 exec 边界。
判定场景参照。它验证了 loop + sandbox + eval 三件套，正好对应我们的 C1 / C6 / C8。

0.2.5 Claude Agent SDK（8k）—— 唯一内核

项内容
它是什么agent harness SDK：loop、流式、工具循环、subagent、hooks、sessions、permissions、MCP。
我们取什么loop、流式、工具循环、subagent 语义、permission 语义。它是 C1 Kernel 的唯一实现来源。
我们不取什么把它当唯一运行时/唯一模型；我们要在它前面加 ModelGateway。
我们要补什么adapter 隔离、模型切换、能力协商、usage 记账。
判定内核唯一来源。不 fork、不重写 loop；所有模型差异在 A1 内部消化。

0.3 编排层参照（2 个补充）

0.3.1 CrewAI（60k）—— Crews ≈ roles，Flows ≈ workflow

项内容
它是什么Crews（角色化自治协作）+ Flows（事件驱动确定性流程）。商业版 AMP 提供控制平面、观测、治理。
我们取什么Flows 的确定性流程（对应我们的 DAG workflow）、Crews 的角色协作（对应 roles + teams）、AMP 的控制平面形态。
我们不取什么AMP 的商业 admin / 云形态；把编排写进代码。
我们要补什么Crews 的 delegation / hierarchical process / 并行协作、memory、事件驱动分支。
判定编排参照。我们的 workflow 目前是 Flows 的线性子集，要补 DAG 与并行。

0.3.2 LangGraph（44k）—— 功能差距最大

项内容
它是什么低层有状态编排框架：durable execution / checkpoint / 任意点 resume、HITL interrupt、长期记忆、subgraph、可视化调试（LangSmith）。
我们取什么DAG 执行、checkpoint、interrupt/resume、subgraph 组合、节点级 trace。
我们不取什么LangSmith 绑定；把图定义写进代码。
我们要补什么图/DAG（分支、并行、循环）、agent 状态 checkpoint（不是只记 step index）、HITL、长期记忆 / store。
判定编排参照，差距最大。我们的 workflow 是它的线性特例；P1 要补 DAG + checkpoint + HITL。
一句话：五家都是 harness；AgentOS 是把 harness 做成自己的 agent OS——同一套 loop，换模型、换工具、换沙箱、换入口，最后加上控制平面。编排层（Crews / 图 / group chat）不是另一套内核，而是同一个 loop 的不同上下文。

TL;DR. 五个问题的答案

问题答案
什么是 agent harness？把 model、tool、session、sandbox 串成可重复循环的运行时。模型是函数，harness 是执行这个函数的程序。
几层架构？5 层：Entry → Kernel → Capabilities → Config → Control Plane。依赖只能向下，不能反向。
几个核心组件？8 个：Kernel、ModelGateway、ToolRegistry、SessionStore、Orchestrator、Sandbox、ConfigLoader、ControlPlane。
几个窄 API？8 个：stream、invoke、run/cancel、append/read/checkpoint、start/resume/interrupt、exec、resolve/dump、record/check。
循环哲学怎么做？一个 loop，五个不变量：append-only、model-visible ⟺ logged、single-writer、cancel-through、budget-hard-stop。多 agent 与 workflow 都是同一个 loop 的不同上下文。
这是 v2 规划稿，不是当前代码事实。它和 v1 的四契约 + 公开 conformance 叙事有 4 处冲突：Knowledge 降级、conformance 取消、preset → profile、框架叙事 → 平台叙事。现状以 agent.html / net.html 为准。

1 什么是 Agent Harness

1.1 定义

Agent harness 是把模型变成 agent 的运行时。它不生产智能，它组织智能：决定模型看到什么上下文、能调用什么工具、会话如何持久、副作用如何受限、循环何时停止。

一句话公式：harness = loop(model, tools, session, sandbox) + policy + observability
模型是可替换的函数；工具是可挂载的能力；session 是事实源；sandbox 是边界；policy 与 observability 是平台属性。

1.2 四个近义词的边界

词它是什么AgentOS 的取舍
Harness执行 agent 循环的运行时：loop + context + tools + session + sandbox我们做这个
Framework供你组合的抽象库：graph、chain、agent 类我们不做通用编排库；只做运行时
Platformharness + 控制平面 + 入口 + 运营我们的产品形态（v2 目标）
Runtime进程/宿主环境（Node、容器、VM）我们只依赖它，不重造它

1.3 一个 harness 必须自己拥有的五件事

职责不拥有的后果
循环（turn / step / tool call）模型只能一次性问答，无法完成多步任务
上下文（system / history / tool schema）行为不可复现，无法调试
会话（append-only 事实源）崩溃即丢失，无法 resume / fork
沙箱（fs / process / network）工具即任意代码执行，无法运营
治理（预算 / 并发 / 审批 / 审计）成本与风险不可控，不能上生产

AgentOS 的立场：这五件事全在 harness 内；模型、工具、知识、入口都在 harness 外，通过窄接口接入。

2.2 每层职责

层职责不做什么
1 Entry协议、鉴权、SSE、UI 适配不跑 loop、不碰模型
2 Kernelturn/step 生命周期、上下文组装、取消、工具循环不知道 provider 细节
3 Capabilities模型通道、工具注册、事件日志、编排、沙箱不互相调用，只经 kernel/contracts
4 Configprofile / bundle / patch 解析、校验、dump不参与运行时决策
5 Control Planetrace、usage、预算、策略、审批、审计、eval不进入业务判断链，只横切

2.3 依赖方向

  • 只能向下：Entry → Kernel → Capabilities → Config；Control Plane 横切。
  • contracts 零依赖；kernel 只依赖 contracts。
  • SDK（Claude Agent SDK）只允许在 kernel/adapter import。
  • Capabilities 之间不互相 import；通过窄 API 或事件交互。
  • 反向依赖在 CI 直接失败。

2.4 为什么是五层

层数判断
三层（Entry / Kernel / Providers）缺少配置层与控制平面，运营能力无处安放
五层（本方案）每层可独立替换；控制平面不污染 loop；配置不进入运行时
七层（再加存储/网络层）过度分层；SQLite/HTTP 是实现细节，不是架构层

3.2 组件边界

C1 Kernel
循环的所有者
  • 输入：session + input + role
  • 输出：事件流 + turn 结果
  • 依赖：C2 / C3 / C4 / C8
  • 不依赖：C5 / C6
C2 ModelGateway
模型通道的所有者
  • 输入：messages + tools + alias
  • 输出：stream + usage
  • 依赖：C7 / C8
  • 不依赖：C3 / C4
C3 ToolRegistry
能力的唯一入口
  • 输入：tool name + args
  • 输出：result / error
  • 依赖：C6 / C8
  • 不依赖：C2
C4 SessionStore
事实源
  • 输入：event
  • 输出：seq / projection / checkpoint
  • 依赖：存储
  • 不依赖：C2 / C3 / C5
C5 Orchestrator
多 agent 与 workflow
  • 输入：role / task / DAG
  • 输出：子结果 / run 状态
  • 依赖：C1 / C4 / C8
  • 不依赖：C2 / C3（经 C1）
C6 Sandbox
副作用边界
  • 输入：argv / fsRoots / network
  • 输出：stdout / exit / files
  • 依赖：OS / 容器
  • 不依赖：C1–C5
C7 ConfigLoader
配置解析
  • 输入：profile / bundle / patch
  • 输出：解析树 / dump
  • 依赖：contracts
  • 不依赖：运行时组件
C8 ControlPlane
观测与治理
  • 输入：span / usage / policy query
  • 输出：decision / audit
  • 依赖：存储 / OTel
  • 不依赖：C1 的业务状态

3.3 组件调用图

flowchart LR K[C1 Kernel] --> M[C2 ModelGateway] K --> T[C3 ToolRegistry] K --> S[C4 SessionStore] K --> CP[C8 ControlPlane] T --> SB[C6 Sandbox] T --> CP O[C5 Orchestrator] --> K O --> S CFG[C7 ConfigLoader] --> M CFG --> T CFG --> O

3.4 组件规则

  • 一个组件一个所有者：每类状态只有一个组件写。
  • 组件不互相 import：只经窄 API 或事件。
  • 组件可替换：C2 换 dialect、C3 换 transport、C4 换存储、C6 换沙箱后端。
  • 组件不藏在 loop 里：新增能力必须是一个组件或一个 provider，不改 C1。

4 几个窄 API

4.1 窄 API 原则

原则含义
一个动词一个方法不提供 "doEverything"；调用方组合
JSON Schema 跨边界不传 TypeScript 类型；不让 zod 跨内核
additive-only加字段不改语义；破坏性变更 major
错误是返回值typed code + retryable，不靠异常控制流
可替换API 稳定，provider 可变

4.4 八个 API 怎么拼成 loop

sequenceDiagram participant E as Entry participant K as Kernel participant S as SessionStore participant M as ModelGateway participant T as ToolRegistry participant C as ControlPlane E->>K: A3 run(session, input) K->>S: A4 append(user/message) K->>M: A1 stream(messages, tools) M-->>K: text / tool_call K->>T: A2 invoke(tool, args) T-->>K: result K->>S: A4 append(tool/result) K->>M: A1 stream(next) M-->>K: final K->>S: A4 append(assistant/message) + checkpoint K->>C: A8 record(usage, span) K-->>E: A3 TurnResult

4.5 为什么是这 8 个

判断理由
少一个 streamKernel 就直接依赖 provider，模型不可切换
少一个 invoke工具散落在 loop 里，无法统一策略/观测
少一个 append会话不可恢复，无法审计
少一个 exec副作用无边界，不能上生产
少一个 resolve配置进入运行时，profile 失效
少一个 record成本/行为不可见，不能运营
再多一个开始出现 "doEverything"；窄接口被破坏

5 循环哲学怎么做

5.1 一个 loop：turn / step / tool / observation

循环不是"让模型多想几轮"，而是一个有状态的执行器：每一步都从事实源取上下文、调用窄 API、把结果写回事实源。

flowchart TB A[turn start] --> B[claim input] B --> C[assemble context] C --> D[model stream] D --> E{tool_call?} E -->|yes| F[policy + sandbox] F --> G[append tool result] G --> D E -->|no| H[append assistant message] H --> I[checkpoint] I --> J[turn end]

5.2 五个不变量

不变量违反的后果
Append-only历史被改写，行为不可复现
Model-visible ⟺ logged模型看到的内容无法回放，审计失效
Single-writer并发写同一 session，事件乱序
Cancel-through取消只停 UI，子进程/工具继续烧钱
Budget hard-stop预算只是提示，成本失控

5.3 循环骨架

loop:
  event = claim_next_input(session)          // A4
  if none: close_turn()
  context = derive_messages(events)          // A4
  decision = control.check_budget(context)    // A8
  if decision != allow: close_turn(denied)
  stream = model.stream(context, tools)      // A1
  for chunk in stream:
    emit(chunk)
    if chunk is tool_call:
      result = tools.invoke(chunk, context)  // A2 → policy → A6
      append(tool_result)                    // A4
      continue loop                          // next step
  append(assistant_message)                  // A4
  checkpoint(session)                        // A4
  close_turn()

5.4 工具循环

阶段动作失败处理

policyallow / deny / approval拒绝 → 回模型；需审批 → 暂停
sandboxfs / process / network越界 → AGT-2005
invoke超时 / 取消AGT-2004，标记 retryable
observe结果（或指针）回填>10KB → offload

5.5 多 agent 循环：同一个 loop

5.6 终止、恢复、取消

runningdoneerror abortedpaused
事件行为

5.7 模型切换不破坏循环

  • loop 只见 Anthropic Messages；vendor 差异在 A1 内部消化。
  • 能力位在启动时协商；缺 tools/streaming → fail fast，不静默降级。
  • fallback 发生在 A1 内部；loop 只看到 "模型换了"，事件与 usage 记录实际模型。
  • translation gateway（OpenAI-compat）是 A1 的实现细节，不是第二套 loop。
